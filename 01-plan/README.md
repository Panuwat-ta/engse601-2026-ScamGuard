## ส่วนที่ใช้ต่อในครั้งที่ 3

คัดลอก **Entry และ Exit Criteria ของทีม** จากใบงานครั้งที่ 1 มาไว้ตรงนี้ด้วย เพื่อให้หาง่าย

| ประเภท | เกณฑ์ของทีม |
|---|---|
| Entry 1 | Baseline ถูกตรึงก่อนเริ่ม: โค้ด `main@66bc9e4a` และ SRS v1.1 (SHA-256 `99bb8d50…cd40a`) พร้อมสภาพแวดล้อมที่ระบุรุ่น (PostgreSQL 15, Redis 7, `alembic upgrade head`) และบันทึกผลการเตรียมฐานข้อมูลไว้ใน evidence |
| Entry 2 | ชุดข้อมูลและเครื่องมือพร้อม: บัญชีทดสอบอย่างน้อย 2 บัญชี (Research Consent = true / false) payload register ที่ปรับค่า consent ได้ สคริปต์เก็บ request/response และคำสั่ง SQL แบบ read-only สำหรับนับแถว `consent_logs` ก่อน–หลัง เกณฑ์เวลาตอบสนองตาม NFR-01 |
| Exit 1 | เคสเชิงลบของ System Consent ครบ 3 แบบ (ส่ง `false` ไม่ส่งฟิลด์ เรียกข้าม client ด้วย payload ปลอม) ต้องได้ HTTP 400 พร้อมข้อความตาม AC-5 และตรวจฐานข้อมูลแล้วไม่มีผู้ใช้/แถว consent เพิ่ม เกณฑ์ผ่าน: Fail 0/3 พร้อมผลรันจริงและ timestamp |
| Exit 2 | วงจร consent ผ่านครบ 4/4 ข้อของ FR-PDPA-01 (บันทึกตอนสมัคร ถอนยินยอม ดูประวัติ หลักฐานยังอยู่หลังลบบัญชี) coverage ของเส้นทาง consent ≥ 80% ตาม NFR-09 ไม่มีข้อบกพร่องระดับ Blocker/Critical ค้าง AC ที่ยังทำไม่ได้ระบุเป็น Not Testable พร้อมเหตุผล |

> Entry 1 เป็น baseline ของ S1 ณ ตอนส่ง (`main@66bc9e4a`) งาน S3 รันบน `Refactor-mobile@c3bc7223`; ตรวจ diff แล้ว `auth.py`/`schemas/auth.py`/models ไม่เปลี่ยน (ต่างที่ `server/app/main.py` +11 บรรทัด)

## ทีมที่ยังไม่มีเอกสารออกแบบของโครงงาน

วาดภาพส่วนประกอบจากโค้ดหรือแผนที่มีจริง แล้วติดป้ายว่า “สร้างย้อนหลัง” หรือเขียนช่องว่างว่าขาดเอกสารใด ใครรับผิดชอบ จะได้เมื่อไร ห้ามแต่งข้อค้นพบที่ไม่ได้ตรวจจริง
